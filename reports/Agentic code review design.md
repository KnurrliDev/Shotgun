# Find many candidates, check each, show few

The evidence supports 1 shape for a review with a large language model (LLM): narrow finders, a verify pass for each candidate, and few issues. More finders and higher effort levels give more recall, but the gain becomes small at the top levels, and the cost does not. Precision comes from the verify pass and from structured facts, not from more agents or more effort. In C and C++, GPT-4 alone named racy variable pairs with recall 0.14, but LLM triage of static alarms reached precision 0.83 to 0.93 (Independent, preprint: [DRB-ML study](https://ar5iv.labs.arxiv.org/html/2308.07505); Industry: [Tencent study](https://arxiv.org/html/2601.18844v1)). Developers act on few, short and correct issues, but independent studies measured only 0.9% to 36.4% action on LLM review comments (Independent: [Sun et al.](https://arxiv.org/html/2508.18771v2); Independent: [Lin et al.](https://arxiv.org/abs/2607.03316)). The Shotgun plan has this shape, but it needs a verify pass at each effort level, far fewer issue steps, and a cap on rounds.

## Labels separate measured results from vendor claims

This report uses 1 term for 1 thing. An issue is a problem that a reviewer reports, and a comment is the post that holds 1 issue. A candidate is an issue before the verify pass, and a finder is an LLM pass or an agent that makes candidates. A verify pass is a later LLM pass that keeps or removes candidates. Sources also call it a validator, a filter or a judge. The action rate is the share of issues that developers act on, and each source defines it differently.

Precision is the share of reported issues that are real. Recall is the share of real issues that the reviewer finds. F1 is the harmonic mean of precision and recall. Numbers from 2 different benchmarks are not comparable, because each benchmark defines its ground truth differently. Each citation starts with 1 of these labels:

| Label | Type of source |
|---|---|
| Independent | A study or a benchmark by authors who do not sell or build the measured tool. "Preprint" shows that the paper had no peer review. "Older" shows a first version from 2023 or earlier. |
| Industry | A paper by the company that built and uses the tool. The data comes from real use, but the authors measure their own tool. |
| Company blog | A blog of a company on an internal tool that it does not sell. Nobody outside the company checked it. |
| Vendor | A claim or a document of a company on a product that it sells. Nobody outside the company checked it. |
| Vendor-run benchmark | A benchmark that a vendor built and runs, with its own tool on the board. |
| Third party | A test, a benchmark or a report by a party that sells no review tool. The sample is small, or nobody reviewed the method. |
| Project claim | A number or a statement that an open-source project gives on itself. |
| Unconfirmed | The research notes saw the claim only in a summary, an abstract or a secondary source. |
| Extract | An added mark: the number came from a search extract of the primary source, not from a full read. |

## The best reviewers still miss about half of the known bugs

Academic benchmarks with real pull requests (PRs) give low scores, and false positives are the main limit. SWR-Bench has 1,000 Python PRs: 500 PRs with changes to review and 500 clean PRs. The best F1 was 19.38%, from PR-Review with Gemini-2.5-Pro, at precision 16.65% and recall 23.18% (Independent: [SWR-Bench](https://arxiv.org/html/2509.01494v2)). 4 tools had precision below 10% (Independent: [SWR-Bench](https://arxiv.org/html/2509.01494v1)). AACR-Bench has 200 PRs in 10 languages, with C and C++, and 1,505 reference comments that 80 engineers labeled. There, Claude-4.5-Sonnet as an agent had precision 39.90% and recall 10.10% (Independent: [AACR-Bench](https://www.alphaxiv.org/abs/2601.19494)).

Commercial tools get higher scores on Martian Code Review Bench, which a party that sells no review tool runs. On 30 July 2026, the top 5 tools had F1 57.5% to 60.8%, precision 64.9% to 76.2% and recall 48.6% to 51.6% (Third party, as a vendor page reports it: [Greptile page about Martian](https://www.greptile.com/content-library/greptile-martian-code-review-benchmark)). Martian itself reports that no tool found more than 63% of the known issues (Third party: [Martian](https://withmartian.com/post/code-review-bench-v0)). A secondary snapshot of October 2026 gave "Claude" F1 61.3%, precision 69.0% and recall 55.2%, but it did not name the product (Third party, through a secondary article: [aicodereviews.io](https://www.aicodereviews.io/blog/martians-code-review-bench-the-1-claim-rots-in-months/)). On GitHub ReviewBench, all 38 configurations had grounded precision of 77.84% to 90.2% and grounded recall of 5.65% to 50.68% (Vendor-run benchmark: [benchmarklist.com copy of the ReviewBench board](https://benchmarklist.com/benchmarks/review_bench/)). Thus the filters of the best tools work, but the best tools still miss about half of the known issues.

The best C data comes from Sashiko, an agentic reviewer for Linux kernel patches. It found about 53% of 1,000 kernel bugs that human reviewers missed, with Gemini 3.1 Pro (Project claim: [LKML post](https://lkml.iu.edu/2603.2/03802.html)). A later internal report on 1,500 email threads gave about 10% false positives and about 85% true positives (Project claim, reported by LWN: [LWN](https://lwn.net/Articles/1073583/)). In AACR-Bench, GPT-5.2 got F1 0.085 on C with the diff only, and the Claude-4.5-Sonnet agent got 0.189 on C. The same agent got 0.247 on Python (Independent: [AACR-Bench](https://arxiv.org/html/2601.19494)). The Greptile, Augment and Martian offline sets contain no C or C++ code, so a C++ team must measure on its own code (Vendor-run benchmark: [Greptile](https://www.greptile.com/benchmarks); Third party: [Martian README](https://github.com/withmartian/code-review-benchmark)).

Numbers from different benchmarks disagree for 4 reasons. First, human review comments miss many real issues: AACR-Bench reports a 285% increase in issue coverage after experts added comments (Independent: [AACR-Bench](https://arxiv.org/html/2601.19494)). Thus correct LLM issues count as false positives, and precision looks too low. Second, each vendor that published a benchmark won its own benchmark (Vendor: [DeepSource](https://deepsource.com/blog/ai-code-review-benchmarks)). Greptile gives itself an 82% catch rate, but the corrected set of Augment gives Greptile an F-score of 45% (Vendor-run benchmark: [Greptile](https://www.greptile.com/benchmarks); Vendor-run benchmark: [Augment](https://www.augmentcode.com/blog/we-benchmarked-7-ai-code-review-tools-on-real-world-prs-here-are-the-results)).

Third, small sets are not stable: in 50-PR sets, a few edge cases can change results by 10 points or more (Vendor: [DeepSource](https://deepsource.com/blog/ai-code-review-benchmarks)). Fourth, LLM reviewers are not deterministic: on SWR-Bench, only 27 correctly found change-points were the same across 5 runs of the same LLM (Independent: [SWR-Bench](https://arxiv.org/html/2509.01494v1)). GitHub tells submitters to run all 219 PRs 3 times (Vendor-run benchmark: [GitHub blog](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/)). This report treats each vendor result as a claim, not as a measurement.

## Three levers, not the number of agents, move precision and recall

No controlled study changes only the number of agents in a review pipeline. The data show 3 separate levers instead. More candidates raise recall and volume, a verify pass raises precision and lowers recall, and tool access helps some models and hurts others. On SWR-Bench, the mean F1 was 18.73% for PR-Review, a careful prompt design, but 9.22% for CR-Agent, a multi-agent tool. The single-pass LLM-Review got 12.49%, and the agent SWR-Agent got 12.61% (Independent: [SWR-Bench](https://arxiv.org/html/2509.01494v2)). In AACR-Bench, the agent mode raised the precision of Claude-4.5-Sonnet from 8.70% to 39.90%, but recall fell from 42.86% to 10.10%.

The agent mode made about 19 times fewer comments, and 4 other models got a much lower F1 with it. GPT-5.2, for example, went from F1 12.19% to 4.59% (Independent: [AACR-Bench](https://arxiv.org/html/2601.19494)). Thus the scaffold and the model must work well together. A self-critique loop does the opposite of a verify pass. In CR-Bench, a Reflexion loop raised the recall of GPT-5.2 from 27.01% to 32.76%, but its signal-to-noise ratio (SNR) fell from 5.11 to 1.95. The share of useful comments fell from 83.63% to 66.10% (Independent: [CR-Bench](https://arxiv.org/html/2603.11078)).

### A verify pass raises precision and lowers recall

Production systems put a verify pass after parallel finders. Anthropic Code Review has 4 stages: Find, Verify, Rank and Post, and in Find, several agents read the diff in parallel (Vendor: [Claude Code docs, Code Review](https://code.claude.com/docs/en/code-review)). The open-source plugin starts 4 finders, then 1 verify subagent for each candidate, and drops each candidate that its subagent did not confirm (Vendor: [code-review command file](https://raw.githubusercontent.com/anthropics/claude-plugins-official/main/plugins/code-review/commands/code-review.md)). The first Cursor Bugbot ran 8 finder passes with a random diff order, a majority vote, a validator model and a dedupe step. Its later agentic design gave the largest gains, and over 40 experiments the resolution rate went from 52% to over 70% (Vendor: [Cursor, Building a better Bugbot](https://cursor.com/blog/building-bugbot)). OpenAI states: "Precision is more important for usability than recall" (Vendor: [OpenAI](https://alignment.openai.com/scaling-code-verification/)).

Measured verify passes trade recall for precision. In BitsAI-CR at ByteDance, the verify pass raised precision from 57.03% to 65.59% and lowered recall from 45.50% to 39.77% (Industry: [BitsAI-CR](https://arxiv.org/html/2501.15134v1)). Lu et al. studied defect-focused review on industrial C++ code at Kuaishou. There, a validator cut the false alarm rate FAR2 from 67.98 to 43.52, and key bug inclusion (KBI) fell from 31.11 to 20.00 (Industry: [Defect-focused ACR](https://arxiv.org/html/2505.17928v2)). KBI is the share of known key bugs that the issues include. The effect differs for each concern: in BitsAI-CR, recall for code defects fell 9.94 points, but performance issues did not change (Industry: [BitsAI-CR](https://arxiv.org/html/2501.15134v1)).

The format of the verdict also matters. In BitsAI-CR, a Conclusion-First verdict gave precision 77.09% and recall 69.00% in 1.7 s for each sample. A Reasoning-First verdict gave precision 65.80% and recall 81.80% in 31.0 s (Industry: [BitsAI-CR](https://arxiv.org/html/2501.15134v1)). A verify pass works best when it gets evidence that the finder did not have, for example a data-flow trace. ZeroFalse gave the LLM each analyzer alarm with flow traces and Common Weakness Enumeration (CWE) context. The best models reached F1 0.912 and 0.955 on 2 Java benchmarks (Independent: [ZeroFalse](https://arxiv.org/abs/2510.02534)).

A verify pass is only as good as the evidence that it adds. An earlier study found that LLMs fail to correct their own answers without external feedback, and that the answers at times became worse (Independent, older: [Huang et al.](https://arxiv.org/abs/2310.01798)). Greptile asked its LLM to give each comment a score from 1 to 10, and the scores were nearly random (Vendor: [Greptile, Make LLMs shut up](https://greptile.com/blog/make-llms-shut-up)). Even a run of code is weak proof. In PoC-Gym, 51 of the 116 exploits that passed the runtime check, about 44%, failed a later check against the true vulnerable location (Independent: [PoC-Gym](https://arxiv.org/abs/2602.04165)). A verify pass must use new evidence, for example more code context, the facts of an engine or a test run, and not a self-score.

### Specialist finders add recall at the same precision

Specialist finders for each concern add recall, but the evidence comes mostly from security tasks. iCodeReviewer from Huawei and partners sends code to prompt experts for each security issue type, on 682 programs with 360 in C and C++. The experts raised recall from 43.30 to 62.68, and precision went from 75.26 to 75.48. In 1 week on 1 production line, C and C++ issues got an acceptance rate of up to 84% (Industry: [iCodeReviewer](https://arxiv.org/html/2510.12186v1)). Anthropic prefers several narrow reviewers to 1 large security prompt, because narrow reviewers do not share blind spots (Vendor: [Anthropic, secure development lifecycle](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)). No study measured specialists for concurrency, logic or tests, and no study compared specialists with generalists at the same token budget.

### Self-scores and majority votes make weak gates

The confidence that an LLM states is a weak gate. For generated code, Spiess et al. found poor alignment between the confidence of the model and correctness (Independent: [Spiess et al.](https://arxiv.org/abs/2402.02047)). Methods that rescale the scores, for example Platt scaling, improved calibration, but they need correctness data first. The README of the Anthropic plugin describes a scorer from 0 to 100 with a threshold of 80 (Vendor: [code-review README](https://raw.githubusercontent.com/anthropics/claude-plugins-official/main/plugins/code-review/README.md)). The current command file has no numeric scale and uses 1 verify subagent for each candidate instead (Vendor: [code-review command file](https://raw.githubusercontent.com/anthropics/claude-plugins-official/main/plugins/code-review/commands/code-review.md)). No vendor published a calibration curve for these thresholds.

A majority vote is also a weak gate, because finder passes rarely agree. The low overlap on SWR-Bench means that a vote removes many true issues that only 1 pass finds. A union of passes with an aggregation step raised recall: 10 runs of Gemini-2.5-Flash raised F1 from 15.25% to 21.91% and recall to 30.44%. The gain became smaller after 5 runs, but the cost increased linearly (Independent: [SWR-Bench](https://arxiv.org/html/2509.01494v2)). In the C++ study of Lu et al., 3 reviewers with a meta-reviewer raised KBI from 26.67 to 31.11 and FAR1 from 83.26 to 87.81 (Industry: [Defect-focused ACR](https://arxiv.org/html/2505.17928v2)). Thus more passes need a verify pass after them, and the low agreement supports a union of the passes, not a vote.

## Engine slices give better review context than retrieved code

Context from program analysis gave the largest measured gains in recall. Lu et al. gave an LLM 4 context levels for industrial C++ changes: the diff, the parent function, Left Flow and Full Flow. Left Flow is a slice of the left-hand values of the change, and Full Flow adds the right-hand values and the signatures of called functions. With LLaMA3.1-405B and 1 reviewer, KBI was 23.70% for the diff, 31.85% for the parent function, 37.04% for Left Flow and 39.26% for Full Flow (Industry: [Defect-focused ACR](https://arxiv.org/html/2505.17928v2)). The ripple of DataFlow, the code that a change reaches, is similar to these slices, so it is the best supported context for Shotgun. But the false alarm rate FAR1 stayed at 75% or more, so context raises recall and does not correct precision.

More context is not always better. Full Flow had a lower combined score than Left Flow, CPI1 20.97 against 22.07, and the authors explain this with distraction from longer context (Industry: [Defect-focused ACR](https://arxiv.org/html/2505.17928v2)). In AACR-Bench, BM25 top-3 retrieval cut the F1 of Claude-4.5-Sonnet from 14.46% to 9.98%, a 31% decrease. The same retrieval raised the F1 of DeepSeek-V3.2 from 9.71% to 15.59% (Independent: [AACR-Bench](https://arxiv.org/html/2601.19494v2)). A raw analyzer report in the prompt of a general reviewer did harm. On SWR-Bench, it cut mean precision from 9.22% to 2.79%, and mean recall went only from 20.39% to 20.04% (Independent: [SWR-Bench](https://arxiv.org/html/2509.01494v1)).

Large code inputs also lower recall in C. o3 found a known kernel use-after-free in 8 of 100 runs with 3.3k lines of code, but in 1 of 100 runs with 12k lines (Third party: [Heelan](https://sean.heelan.io/2025/05/22/how-i-used-o3-to-find-cve-2025-37899-a-remote-zeroday-vulnerability-in-the-linux-kernels-smb-implementation/)). In the Tencent study, the alarms that all methods missed had functions about 95.6 lines longer than average, with about 21 more conditions (Industry: [Tencent study](https://arxiv.org/html/2601.18844v1)). Atlassian found that context from other repositories either had no effect or made the review worse (Vendor: [Atlassian blog, PR context](https://www.atlassian.com/blog/development/improving-code-reviewer-with-pr-context)). Thus the evidence supports a small slice for each finder: the hunk, its ripple and its facts, not whole files or search results.

Text that states the intent of the change gave the largest gain in 1 benchmark. In ContextCRBench, the mean F1 of closed-source models for quality estimation went from 36.08 with the diff only to 62.12 with the PR description. With text and code together, it reached 64.74, but code context alone gave 51.76 (Independent: [ContextCRBench](https://arxiv.org/html/2511.07017v1)). In that data, the PR description often states the fix, so a part of the gain can come from a hint to the answer. No study measured if a review against the spec finds requirements that the change does not implement. Project rules also help: a taxonomy of 219 rules raised the precision of BitsAI-CR from 16.83% to 57.03% (Industry: [BitsAI-CR](https://arxiv.org/html/2501.15134v1)).

The outcomes of past reviews are another strong input. In an online test of Atlassian, a similar past PR with its review comments raised the resolution rate from 31.92% to 41.90% (Vendor: [Atlassian blog, PR context](https://www.atlassian.com/blog/development/improving-code-reviewer-with-pr-context)). In Shotgun, the closed issues and their reasons in the ledger are the same type of input. Agent tool calls help most when the issue needs context outside the diff, and about 15.5% of real comments in AACR-Bench need repository context (Independent: [AACR-Bench](https://arxiv.org/html/2601.19494v2)). The guidance of Anthropic is the smallest set of high-signal tokens, and each subagent returns a summary of often 1,000 to 2,000 tokens (Vendor: [Anthropic, Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Thus a small packet of engine facts first, then tool calls on demand, agrees with the evidence, but no study measured this hybrid for review.

## An LLM fails as a race finder and works as a judge of engine facts

An LLM alone can say if a small program has a race, but it rarely names the 2 racy accesses. On 198 C and C++ OpenMP programs of DataRaceBench, GPT-4 gave the race verdict at F1 0.751 to 0.757, near the 0.762 of Intel Inspector. When it also had to name the variable pair, the lines and the read or write type, its F1 fell to 0.193 (Independent, preprint: [DRB-ML study](https://ar5iv.labs.arxiv.org/html/2308.07505)). On 34 SV-COMP pthread programs, GPT-4o and GPT-4o-mini had race recall 1.00 at precision 0.24, so they said race for almost all programs. No model of the 5 gave a true deadlock positive, and 3 models reported races in race-free code with atomics (Independent, preprint: [Jain and Purandare](https://arxiv.org/html/2501.14326v2)). No benchmark of 2025 or 2026 measured models such as o3, GPT-5 or Claude 4.x on DataRaceBench or on deadlocks.

Memory and lifetime bugs show the same pattern. On PrimeVul, GPT-4 had to label a vulnerable C or C++ function and its patched version correctly. It got 5.14% with two-shot prompts and 12.94% with chain of thought, but a random guess got 22.70% (Independent, extract: [PrimeVul](https://arxiv.org/pdf/2403.18624)). For more than 90% of the functions in common datasets, nobody can decide the vulnerability without more context (Independent, extract: [Risse, Liu and Böhme](https://arxiv.org/abs/2408.12986v2)). On a known use-after-free in the Linux SMB server, o3 had 8 hits in 100 runs, and Claude Sonnet 3.7 had 3 (Third party: [Heelan](https://sean.heelan.io/2025/05/22/how-i-used-o3-to-find-cve-2025-37899-a-remote-zeroday-vulnerability-in-the-linux-kernels-smb-implementation/)). RepoAudit, an agent with a validator of data-flow facts and path conditions, found 40 true bugs in 15 projects at precision 78.43% (Independent, extract: [RepoAudit](https://icml.cc/virtual/2025/poster/45170)).

Hybrids of a static analyzer and an LLM give the strongest results. In LLift, the same LLM went from F1 0.13 with a simple prompt to 0.93 with post-constraints, task decomposition and self-validation (Independent: [LLift](https://www.cs.ucr.edu/%7Ezhiyunq/pub/oopsla24_llift.pdf)). In the Tencent study on C and C++ alarms, LLM4PFA gave static path constraints to an agent. It reached precision 0.83 to 0.93 and recall 0.75 to 0.88, and it removed 94% to 98% of the false positives. LLM4SA, with hundreds of lines of code around the sink, reached only precision 0.63 to 0.85 (Industry: [Tencent study](https://arxiv.org/html/2601.18844v1)). With GPT-4o, LLM4PFA needed $0.020 and 12.6 s for each alarm, but a manual review takes 10 to 20 minutes.

Other hybrids show the same split of work. BugLens raised the precision of kernel taint warnings from 0.10 to 0.72 (Independent, preprint, extract: [BugLens](https://arxiv.org/abs/2504.11711v3)). In KNighter, an LLM wrote Clang Static Analyzer checkers from past kernel fixes, and the checkers found 92 new bugs, 77 confirmed and 57 fixed (Independent, extract: [KNighter](https://arxiv.org/abs/2503.09002v3)). At Uber, Dr.Fix gave the LLM the 2 stacks of each race from the Go race detector, which uses ThreadSanitizer. In 18 months, 224 of 404 races got a validated fix, and developers accepted 193 of these 224 fixes (Industry: [Dr.Fix](https://arxiv.org/html/2504.15637)). Theori RoboDuck gave each Infer report a score with a 1-token LLM call, and only the top 20% went to an agent (Company blog: [Theori blog](https://theori.io/blog/aixcc-and-roboduck-63447)).

In each hybrid, the analyzer gives recall and structure, and the LLM checks if a specific path or report is feasible. No study measured the value of thread entry points, lock sets or shared-access facts for an LLM reviewer, so the table below is an inference. It copies the facts that Dr.Fix gets from a dynamic race report, and it uses the split of work of the hybrids above. DataFlow gives the threads, the shared data with races, the locks and the call graph. This report does not know if DataFlow also gives lock-order cycles, memory orders or the capture lists of lambdas.

| Bug class | Facts for the LLM | Task of the LLM | Evidence |
|---|---|---|---|
| Data race | The 2 accesses with file, line, field and read or write type. The thread entry points that reach each access, with the call paths. The lock set at each access, the atomics with their memory order, and the happens-before edges. | Decide if the 2 accesses can occur at the same time. Write the interleave and the effect. | GPT-4 named race pairs at F1 0.193 (Independent, preprint: [DRB-ML study](https://ar5iv.labs.arxiv.org/html/2308.07505)). Dr.Fix used 2 stacks and their common ancestor (Industry: [Dr.Fix](https://arxiv.org/html/2504.15637)). |
| Deadlock | The lock-order cycle, with the sites that get each lock and the call paths. | Decide if the threads can run these paths at the same time. | 5 models gave no true deadlock positive without facts (Independent, preprint: [Jain and Purandare](https://arxiv.org/html/2501.14326v2)). |
| Lifetime of a lambda or a thread | The capture list of each lambda that goes to a thread or an executor. The scope end of each captured object, and the join and detach points. | Decide if the object can end before its last use. | Without annotations, Clang Lifetime Safety Analysis can miss dangling pointers across calls (Project claim, extract: [Clang documentation](https://clang.llvm.org/docs/LifetimeSafety.html)). |
| Null pointer and bounds | The path constraints of the alarm. | Decide if the path is feasible. | LLM4PFA reached precision 0.83 to 0.93 (Industry: [Tencent study](https://arxiv.org/html/2601.18844v1)). |

A race fact that the LLM rejects must stay visible with its reason, because in the Tencent study, triage recall was only 0.65 to 0.88 (Industry: [Tencent study](https://arxiv.org/html/2601.18844v1)). Concurrency issues are also hard to explain: Coverity did not release concurrency checkers for many years for this reason (Industry: [Bessey et al.](https://6826.csail.mit.edu/2019/papers/coverity.pdf)). At Facebook, the concurrency analysis had a fix rate of about 50%, against more than 70% for the general diff analysis. Developers still valued these reports, because concurrency bugs are hard to debug (Industry: [Distefano et al.](https://6826.csail.mit.edu/2020/papers/facebook-infer-cacm.pdf)). Thus a race issue needs a written interleave of the 2 threads. No source measured a sanitizer run as proof for review issues in C or C++.

Of the benchmarks in this report, only ReviewBench has data for each effort level. On it, recall rises with effort and then becomes flat. The table gives the board of 29 October 2026 for Codex.

| max | 1 | 12 | $18.73 | 24 min |

Source: Third party: [bestagent.dev](https://bestagent.dev/claude-code-review-effort-levels-tested-2026).

Medium already found all 12 bugs, and the cost of max was more than 50 times the cost of xhigh, with no gain in recall. At max, the review used 30 agents: 9 finders, 19 verifiers and 1 sweep. On the fixed change, the review still reported 1 issue at low, 10 at medium, 8 at high, and 15 at xhigh and at max. Most of these were suggestions, not real defects. The authors state that the runs are too few to separate random variation from real differences between the levels (Third party: [bestagent.dev](https://bestagent.dev/claude-code-review-effort-levels-tested-2026)). A gain from max probably needs large diffs with many interactions, but no source measured this.

Repeated samples also lose value fast. On SWR-Bench, 5 runs of Gemini-2.5-Flash got F1 20.48% at $3.68E-03 for each PR, and 1 run of Gemini-2.5-Pro got 19.38% at $5.86E-03 (Independent: [SWR-Bench](https://arxiv.org/html/2509.01494v2)). Thus several runs of a cheaper model can do better than 1 run of a stronger model, at a lower cost.

Anthropic Code Review sends more agents to large changes and a light pass to trivial changes. At Anthropic, 84% of PRs with more than 1,000 changed lines got issues, with 7.5 issues on average. Of the PRs with less than 50 changed lines, 31% got issues, with 0.5 issues on average (Vendor: [Anthropic](https://claude.com/blog/code-review)). Recall also falls on large changes: on SWR-Bench, it fell from 38.35% for PRs with 1 change-action to 8.88% for PRs with 5 or more (Independent: [SWR-Bench](https://arxiv.org/html/2509.01494v2)). OpenAI found that recall fell faster at a lower thinking budget on code that Codex wrote than on code that humans wrote (Vendor: [OpenAI](https://alignment.openai.com/scaling-code-verification/)). This matters for Shotgun, because Claude reviews code that Claude wrote.

## Developers act on issues that are few, short, local and correct

Developers judge a tool by the share of issues that they do not act on. Google lets a code review check have up to 10% effective false positives, which are issues that developers take no positive action on (Industry: [Sadowski et al.](https://6826.csail.mit.edu/2020/papers/google-analysis-cacm.pdf)). In a survey of 375 Microsoft developers, 90% accept a false positive rate up to 5%, but only 24% accept 20% (Independent: [Christakis and Bird](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/07/ase-2016.pdf)). The Coverity founders write that users ignore a tool above 30% false positives, and reject it if about the first 3 reports are false (Industry: [Bessey et al.](https://6826.csail.mit.edu/2019/papers/coverity.pdf)). Placement matters as much as precision. With the same analysis, Infer got almost no fixes from nightly reports, but a fix rate above 70% at diff time (Industry: [Distefano et al.](https://6826.csail.mit.edu/2020/papers/facebook-infer-cacm.pdf)).

LLM reviewers are far from these budgets in independent data. In 16 automated review actions on GitHub, only 0.9% to 19.2% of the comments were valid and addressed, against 60% of valid human comments (Independent: [Sun et al.](https://arxiv.org/html/2508.18771v2)). In a study of 31,073 pairs of CodeRabbit comments and replies, developers accepted 36.4% and rejected 56.3%, mostly because of invalid suggestions (Independent: [Lin et al.](https://arxiv.org/abs/2607.03316)). At Mozilla and Ubisoft, reviewers accepted only 8.1% and 7.2% of the comments of RevMate (Independent: [Olewicki et al.](https://arxiv.org/html/2411.07091v1)). Company tools with strong filters come nearer to people: Atlassian measured 38.70% against 44.45% for human comments, and Uber 65% against 51% (Industry: [RovoDev](https://arxiv.org/html/2601.01129v2); Company blog: [Uber, uReview blog](https://www.uber.com/us/en/blog/ureview/)). Each team that reports good rates added filters after generation, and the metrics differ, so these values are upper bounds.

4 properties raise action: code that the author can apply, a precise location, a short text and a stated reason. In the GitHub study, the addressed rate went from 4.2% for comments with no code to 23.2% for comments with more than 52% code. Longer text had a negative association with code changes, ρ = −0.24. Tools that comment on each hunk generally did better than tools that comment on each file (Independent: [Sun et al.](https://arxiv.org/html/2508.18771v2)). At Google, 75% of the bugs filed against 1 analyzer came from users who misunderstood its message text (Industry: [Tricorder](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/43322.pdf)). No study measured a concrete failure scenario alone, but filters that remove likely fake problems support it indirectly.

Developers act most on correctness and least on style. At Uber, developers rated readability nits, small log tweaks, low-impact performance changes and style as poor, but rated correctness bugs and absent error handling well (Company blog: [Uber, uReview blog](https://www.uber.com/us/en/blog/ureview/)). Agent suggestions for tests got 7.6% adoption, against 16.7% for defect suggestions (Independent: [Human-AI Synergy study](https://arxiv.org/html/2603.15911v1)). But the data are mixed. At Mozilla and Ubisoft, reviewers accepted comments on code structure at 18.2% and 18.6%, but functional comments only at 4.8% and 5.2%. Many functional comments were wrong, so a verify pass is necessary for functional issues (Independent: [Olewicki et al.](https://arxiv.org/html/2411.07091v1)).

Production systems now share 1 pattern with 8 parts:

Feedback loops gave large gains: the similarity filter of Greptile raised the address rate from 19% to more than 55% in 2 weeks (Vendor: [Greptile blog](https://www.greptile.com/blog/make-llms-shut-up)). Google suppressed 17 best-practice links that raters found not actionable, and the useful ratio rose from 54% to 66% (Industry: [AutoCommenter](https://arxiv.org/html/2405.13565v1)). Explicit feedback is rare: developers gave it on about 10% of AutoCommenter comments in review and on 2% in the integrated development environment (IDE). There are 2 directions of failure: a noisy reviewer loses trust, and a cautious reviewer misses bugs, as the early agentic Bugbot did (Vendor: [Building a better Bugbot](https://cursor.com/blog/building-bugbot)). Thus a design needs 2 metrics together: the issues that the user fixed for each review, and the rate of action.

No study compared the same LLM issues before the commit in an IDE and after the push in a PR. In the Microsoft survey, developers prefer results in the editor, and 24% want analysis when the change is complete, before the review request (Independent: [Christakis and Bird](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/07/ase-2016.pdf)). Shotgun runs its review at this point, so the placement agrees with the evidence. A review before the commit loses peer accountability, because nobody else sees which issues the author ignored (Industry: [Tricorder](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/43322.pdf)). The ledger of Shotgun and Copy for the pull request already carry the issues and their states into the PR. Reviewers who started from an LLM review covered fewer lines, 371 against 484, so a list of issues can narrow the attention of the user (Independent: [Tufano et al.](https://arxiv.org/html/2411.11401v3)).

## The Shotgun plan, part by part, against the evidence

This section takes section 6.10, the decisions 35 to 37 and the proposals P19 to P23 of the implementation plan. For each part, it says what the evidence supports, what it contradicts, and what to change. The plan already has the main pattern of the evidence. It reviews the whole task, checks candidates in a verify pass, puts the most severe issues first, and reviews only new and changed hunks later. The largest gaps: low has no verify pass, max can give 32 issue steps, plausible issues become steps, and the rounds have no cap.

### The effort table: put a verify pass at each level

The evidence supports 3 parts of the table. Medium as the default agrees with the third-party test, where medium found all 12 planted bugs for $0.13 to $0.14 (Third party: [bestagent.dev](https://bestagent.dev/claude-code-review-effort-levels-tested-2026)). A finder for each focus area agrees with the prompt experts of iCodeReviewer and the separate stages of Sashiko (Industry: [iCodeReviewer](https://arxiv.org/html/2510.12186v1); Project claim: [Sashiko README](https://github.com/sashiko-dev/sashiko)). A verify pass for each candidate agrees with the plugin of Anthropic, BitsAI-CR and Lu et al. (Vendor: [code-review command file](https://raw.githubusercontent.com/anthropics/claude-plugins-official/main/plugins/code-review/commands/code-review.md); Industry: [BitsAI-CR](https://arxiv.org/html/2501.15134v1)).

The evidence contradicts low with no verify pass. The `/code-review` documentation says that low gives fewer false positives, but nobody published its precision (Vendor: [Claude Code docs, /code-review](https://code.claude.com/docs/en/code-review-local)). The issues that Claude is most sure of have no measured precision, because the confidence that an LLM states has poor calibration (Independent: [Spiess et al.](https://arxiv.org/abs/2402.02047)). A Conclusion-First verdict has a low cost: 1.7 s for each sample in BitsAI-CR (Industry: [BitsAI-CR](https://arxiv.org/html/2501.15134v1)). The first issues that a user sees decide trust, and low is the cheapest level for a first try (Industry: [Bessey et al.](https://6826.csail.mit.edu/2019/papers/coverity.pdf)). In the third-party test, low also found only 5 and 4 of the 12 bugs in 2 of its 3 runs (Third party: [bestagent.dev](https://bestagent.dev/claude-code-review-effort-levels-tested-2026)).

The table puts the ripple only at xhigh, but the ripple is similar to the context with the best measured gain (Industry: [Defect-focused ACR](https://arxiv.org/html/2505.17928v2)). No study measured the callers of changed functions as a separate context. Max adds a second verify pass, and vendor practice supports more than 1 verifier: at Anthropic, a group votes on each issue (Vendor: [claude.dev blog](https://claude.dev/blog/solving-code-review-at-anthropic/)). But no study measured the gain of a second verifier, and a second pass with the same evidence repeats the self-critique problem. In the third-party test, the cost of max was $18.73, against $0.32 to $0.36 for xhigh, with no gain in recall (Third party: [bestagent.dev](https://bestagent.dev/claude-code-review-effort-levels-tested-2026)). Thus the second verifier at max must use new evidence, for example the engine facts or a sanitizer run.

From high, the table puts plausible issues into the list, and each issue becomes a step of the user. The evidence supports a list of plausible issues, because a strict verify pass lowers recall: in Lu et al., KBI fell from 31.11 to 20.00 (Industry: [Defect-focused ACR](https://arxiv.org/html/2505.17928v2)). But it contradicts plausible issues as steps by default, because developers judge a tool by its non-action, and Google keeps it at 10% or less (Industry: [Sadowski et al.](https://6826.csail.mit.edu/2020/papers/google-analysis-cacm.pdf)). CodeRabbit has a quiet profile that moves minor comments into a summary, and Tricorder shows only important results (Vendor: [CodeRabbit docs](https://docs.coderabbit.ai/reference/configuration); Industry: [Tricorder](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/43322.pdf)). Thus plausible issues belong in a second list that the user can open, and the user can make 1 of them a step.

The changed table below applies these points. No source measured this table as a whole, so it is a proposal from the evidence.

| Effort | Finders | Context | Verify pass | Steps and second list |
|---|---|---|---|---|
| low | 1 generalist finder in a fresh subagent | The hunks, and the DataFlow facts of the changed functions | 1 short Conclusion-First verdict for each candidate | Confirmed issues as steps. No second list. |
| medium, the default | 1 finder for each focus area | Also the ripple of each hunk, and the read tools of DataFlow on demand | 1 verify subagent for each candidate, with a file:line citation and a DataFlow fact for each claim | Confirmed issues as steps. Plausible issues in the second list. |
| high | As medium, and a second pass with a different hunk order | As medium | As medium. Reasoning-First verdicts for race and lifetime candidates. | As medium |
| xhigh | As high, and 1 more sample for each hot changed function | Also the callers of each hot changed function | As high | As medium |
| max | As xhigh, with up to 5 samples for the race and lifetime finders | As xhigh | A second verifier only with new evidence, for example a sanitizer run that the user agrees to | As medium |

### The focus areas: keep the engine areas, and narrow tests and cleanups

The 6 areas agree with the evidence on what developers act on, with 2 exceptions. Correctness, threads and races, and lifetime cover the categories that developers rate highest (Company blog: [Uber, uReview blog](https://www.uber.com/us/en/blog/ureview/)). The GitHub study also found a positive association between concurrency and lock topics and code changes (Independent: [Sun et al.](https://arxiv.org/html/2508.18771v2)). The brief area agrees with the large gain from intent text in ContextCRBench, but no study measured a check for absent requirements (Independent: [ContextCRBench](https://arxiv.org/html/2511.07017v1)). Also, Claude wrote the plan and many lines of the task, so it can misread the brief in the review as in the code.

The first exception is tests. Generic test requests get little action: agent suggestions for tests got 7.6% adoption, and Graphite found comments that ask for tests correct but unwanted (Independent: [Human-AI Synergy study](https://arxiv.org/html/2603.15911v1); Unconfirmed: [CS146S summary](https://fireman333.github.io/CS146S-handbook-zh/readings/w7_lessons_from_millions_of_ai_code_reviews/)). The plan limits the area to a condition of done with no test, and this agrees with the plugin rule for explicit requirements. The second exception is cleanups, which `/code-review` covers at some levels, but which the Claude Code team drops (Vendor: [claude.dev blog](https://claude.dev/blog/solving-code-review-at-anthropic/)). Uber developers rated low-impact performance changes as poor, so the default focus can leave out cleanups and keep them on request. A level-4 step for a cleanup needs much work, but Meta found that generated patches work well for small changes such as renames (Industry: [Maddila et al.](https://arxiv.org/html/2507.13499v1)).

The threads area describes only data races. Deadlocks and false races on atomics need explicit facts, because no model found a true deadlock and 3 models reported races in code with atomics (Independent, preprint: [Jain and Purandare](https://arxiv.org/html/2501.14326v2)). Thus the area can add deadlocks with a lock-order cycle, if DataFlow can give the cycle. The lifetime area can add leaks and double frees, as the resources stage of Sashiko does (Project claim: [Sashiko README](https://github.com/sashiko-dev/sashiko)). Developers rank security first, but the plan has no security area, so null pointer and bounds issues need a place in correctness or lifetime (Independent: [Christakis and Bird](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/07/ase-2016.pdf)).

### The verify pass: correct idea, but start it at low and give it new evidence

The plan checks the failure scenario of each candidate, and this agrees with the fake-problem check of Lu et al. (Industry: [Defect-focused ACR](https://arxiv.org/html/2505.17928v2)). The rule that each issue names the DataFlow tools that show it agrees with the file:line evidence rule of Anthropic (Vendor: [Customize Code Review](https://code.claude.com/docs/en/code-review-customize)). The evidence gives 4 changes. First, start the verify pass at low with a short Conclusion-First verdict, because the cost is small and trust starts with the first issues. Second, run each verifier in a fresh subagent with only the candidate, the slice and the facts, because self-correction without new evidence is weak. Third, set the strictness for each area, because the recall cost of BitsAI-CR differed for each concern (Industry: [BitsAI-CR](https://arxiv.org/html/2501.15134v1)).

Fourth, define plausible more strictly. The plan calls an issue plausible when the verify pass did not confirm it and found no proof against it. That class can hold much of the noise, because the error analysis of AACR-Bench traced incorrect comments to unverified speculation (Independent: [AACR-Bench](https://www.alphaxiv.org/abs/2601.19494)). A plausible issue from an engine fact, for example a race pair of DataFlow, is different from a plausible issue from the LLM alone. Thus the second list can show the source of each plausible issue: engine or model, as decision 13 does with its badges.

### The parts of an issue: add a severity and an origin

Most parts of P19 have direct support. The 1-sentence summary and the category tag copy the format of `/code-review` in a host app (Vendor: [Claude Code docs, /code-review](https://code.claude.com/docs/en/code-review-local)). The short title and summary agree with the negative association of length and action, ρ = −0.24 (Independent: [Sun et al.](https://arxiv.org/html/2508.18771v2)). The place with a short text of its code agrees with the evidence for local comments on changed lines (Industry: [Tricorder](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/43322.pdf)). Up to 4 more places for the fix agree with 1 issue for a class of bug, as the Claude Code team and Copilot do (Vendor: [claude.dev blog](https://claude.dev/blog/solving-code-review-at-anthropic/); Vendor: [GitHub blog](https://github.blog/ai-and-ml/github-copilot/60-million-copilot-code-reviews-and-counting/)). The DataFlow tools of each issue give the evidence that a verifier and the user can check, as decision 13 does for the survey.

2 parts are absent. First, the issue has no severity, but the list puts the most severe issues first, so the order has no recorded basis. Anthropic ranks by Important, Nit and Pre-existing, and Lu et al. sort and cut by a severity score (Vendor: [Read and request reviews](https://code.claude.com/docs/en/code-review-pull-requests); Industry: [Defect-focused ACR](https://arxiv.org/html/2505.17928v2)). A severity field with few levels agrees with this, and Tricorder removed visible severity levels and showed only important results (Industry: [Tricorder](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/43322.pdf)). Second, the issue does not say if the task added the problem or if the problem was there before the task. The ripple reaches unchanged code, so the review can find old bugs, and these need the Pre-existing label of Anthropic, not a step (Vendor: [Read and request reviews](https://code.claude.com/docs/en/code-review-pull-requests)).

The failure scenario needs a fixed form. The evidence supports a trigger, a path through the changed code and a wrong result, because a verifier can check each part against the code. For a race, the form is the 2 accesses and 1 interleave of the 2 threads that gives the wrong result. Coverity held back concurrency checkers for years, because the errors were too hard to explain (Industry: [Bessey et al.](https://6826.csail.mit.edu/2019/papers/coverity.pdf)). Code in a comment raised the addressed rate from 4.2% to 23.2% (Independent: [Sun et al.](https://arxiv.org/html/2508.18771v2)). In Shotgun, the user writes the fix, so the open decisions of the issue take this role.

### The maximum numbers of issues: cap the steps by the size of the diff, not by the effort

No study varied a maximum number of issues and measured the action rate. The values 5, 10, 20, 25 and 32 have no direct evidence, and 32 copies the limit of `/code-review` for its report tool (Vendor: [Claude Code docs, /code-review](https://code.claude.com/docs/en/code-review-local)). The reported volumes are lower: 2.1 comments for each PR at Atlassian, 0.4 to 0.7 bugs for each Bugbot run, and about 5.1 at GitHub (Industry: [RovoDev](https://arxiv.org/html/2601.01129v2); Vendor: [Building a better Bugbot](https://cursor.com/blog/building-bugbot); Vendor: [GitHub blog](https://github.blog/ai-and-ml/github-copilot/60-million-copilot-code-reviews-and-counting/)). Anthropic found 0.5 issues on average below 50 changed lines and 7.5 above 1,000 lines (Vendor: [Anthropic](https://claude.com/blog/code-review)). Thus the size of the diff, not the effort level, can set the cap on steps. Each issue in Shotgun is a step of the user, so a false issue has a higher cost than an ignored PR comment.

A cut must not delete real issues. In Lu et al., a Top-5 cut instead of Top-10 lowered KBI from 32.59 to 25.93, and FAR1 changed only from 91.13 to 90.15 (Industry: [Defect-focused ACR](https://arxiv.org/html/2505.17928v2)). Thus precision comes from the filter before the cut, and the cut only hides issues. The change: keep 1 cap on steps for all effort levels, and scale it with the size of the diff. Put the confirmed issues above the cap and all plausible issues into the second list, and let the user make any of them a step. The ledger can then measure the non-action rate by rank, and the cap can move to the rank where non-action passes about 10%.

### The issue steps: a strong source of feedback with a high cost for each issue

The steps give Shotgun something that no vendor has: an explicit decision with a reason for each issue. Other tools get explicit feedback on less than 4% to about 10% of their comments (Unconfirmed: [CS146S summary](https://fireman333.github.io/CS146S-handbook-zh/readings/w7_lessons_from_millions_of_ai_code_reviews/); Industry: [AutoCommenter](https://arxiv.org/html/2405.13565v1)). Feedback loops gave large gains at Greptile, Google and Cursor, so the reasons of Not a problem are a strong input for the next review. The order of the list, the most severe issues first, agrees with the rank of Anthropic and the sort of Lu et al. The gate that never waits agrees with the results of Anthropic, Cursor and GitHub that never block a merge (Vendor: [Claude Code docs](https://code.claude.com/docs/en/code-review); Vendor: [Bugbot docs](https://cursor.com/docs/bugbot)).

The cost of each step is the problem. A level-4 step asks the user to write each fix, also for a plausible issue or a 1-line cleanup. The evidence on action supports fixes that the author can apply: Google authors applied 40% to 50% of the previewed edits (Company blog: [Google Research blog](https://research.google/blog/resolving-code-review-comments-with-ml/)). But decision 37 serves the goal of the plan, code that the user owns, and no source measured ownership or what the user learns. Thus the evidence cannot decide this choice, and the user must decide it. 1 option agrees with both: an issue with no open decision gets the rule of P30, the lower of the heat level and 2.

Each step can start with 1 question: is the issue real? The user answers it with Not a problem or with a fix, and the ledger records the answer for the calibration of the verify pass. Spiess et al. show that methods that rescale scores need such correctness data, and the ledger already has this data (Independent: [Spiess et al.](https://arxiv.org/abs/2402.02047)).

### The rounds: add a cap, a match by similarity and the ripple of the fixes

P23 agrees with the changes that Anthropic made after 1 PR went through more than 50 review rounds in 1 night. Anthropic now reviews only the diff after the first passes, repeats no posted issue, and flags the class of bug, not 1 line (Vendor: [claude.dev blog](https://claude.dev/blog/solving-code-review-at-anthropic/)). Then PRs that passed after 1 round rose from 65% to 78%, and PRs with 5 or more rounds fell from 8.9% to 1.5%. The hunk hashes of P23 give the same scope. The check of each fixed issue agrees with Anthropic Code Review, which resolves its own threads when it judges an issue fixed (Vendor: [Read and request reviews](https://code.claude.com/docs/en/code-review-pull-requests)). At Beko, developers complained that each fix produced a new review (Independent: [Cihan et al.](https://arxiv.org/html/2412.18531v2)).

3 parts are absent from P23. First, the rounds have no cap, but Anthropic asks the author to reconsider the approach after 3 rounds, and Sourcery stops automatic re-reviews after 5 (Vendor: [claude.dev blog](https://claude.dev/blog/solving-code-review-at-anthropic/); Vendor: [Sourcery docs](https://docs.sourcery.ai/reviews/anatomy-of-a-review/)). In Microsoft data, 83% of human comments came in the first 2 iterations, and later comments were less likely to be useful (Independent: [Bosu, Greiler and Bird](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/bosu2015useful.pdf)). Second, submit_review matches an issue by its place and title, but the same LLM gives different issues and titles in each run (Independent: [SWR-Bench](https://arxiv.org/html/2509.01494v1); Third party: [LWN](https://lwn.net/Articles/1073583/)). A match by similarity, as in BitsAI-CR and Greptile, is better (Industry: [BitsAI-CR](https://arxiv.org/html/2501.15134v1); Vendor: [Greptile](https://greptile.com/blog/make-llms-shut-up)). The rule of the plan for closed callouts can also cover closed issues: Claude names them again only with new evidence.

Third, the next round reviews only the new and the changed hunks, but a fix can break code that its hunks reach. Thus the scope of the next round can add the ripple of the new hunks, not the ripple of the whole task. The rule to flag the class of bug also helps, because P19 already gives up to 4 more places for each issue.

## Conclusion

In Shotgun, an issue is not a comment that a developer can skip. It is a step that the user must close. Thus a false issue has a higher cost than in a PR tool. The 10% non-action budget of Google is a limit for Shotgun, not a target. The same design gives Shotgun an advantage that vendors do not have: a recorded decision with a reason for each issue. With it, Shotgun can calibrate its verify pass for each focus area on the code of the user, and no vendor published such a calibration.

The engine changes the task of the LLM in the review. Without facts, the LLM must search for races, and the search fails. With the facts of DataFlow, the LLM judges a given race, and the best results in the evidence came from such tasks. Thus the value of a Shotgun review comes from its engine facts and its verify pass, not from more agents or more effort. Recall stays the open question, because the best tools still miss about half of the known bugs. No data shows how much engine facts reduce this gap for C++.
